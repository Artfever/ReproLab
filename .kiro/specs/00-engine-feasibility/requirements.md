# Requirements Document

## Introduction

ReproLab is an open-source project that helps researchers run a supported old analysis with its original engine. This milestone proves only one thing: the original OpenBUGS engine can run a real analysis (the Seeds example) on Linux x86-64, with genuine logs and outputs, inside a pinned and reproducible environment. It contains no Next.js site, no AI assistant and no cloud deployment.

The milestone also records what it could not establish. Licence questions, an unverified upstream checksum, a baseline transcribed from an image, and a post hoc setting choice are all documented. Unresolved licence, provenance or runtime issues block both the later Web_Runner and any Image_Distribution of the Engine_Image. The licence review is INCOMPLETE and must not be described as complete in any document of this milestone. The evidence for this milestone is in `docs/engine-feasibility.md` and `docs/evidence/`; the licence evidence is in `docs/licensing-review.md`, `docs/release-inventory.md` and `docs/third-party-notices.md`; the distribution gate is in `docs/release-decision.md`.

## Glossary

- **Feasibility_Harness**: The set of scripts, Dockerfile, Python adapter and documents in this repository that build the engine image, run analyses and record evidence.
- **OpenBUGS**: The original Bayesian analysis engine, version 3.2.3, built from the Linux source package.
- **Engine_Image**: The pinned linux/amd64 container image that contains the OpenBUGS build and the adapter.
- **Adapter**: The typed Python module in the Feasibility_Harness that generates the batch script, starts the engine, classifies the outcome and writes the Run_Manifest.
- **Batch_Script**: The OpenBUGS script file generated by the Adapter and executed with the `-t` option.
- **Seeds_Example**: The OpenBUGS Seeds tutorial: 21 plates, a random-effects logistic regression, one model file, one data file, and two separate initial-value files (one per chain).
- **Monitored_Nodes**: The five nodes `alpha0`, `alpha1`, `alpha2`, `alpha12` and `sigma`.
- **Run**: One execution of the engine on one set of inputs and settings.
- **Run_Manifest**: A JSON file written for each Run that records inputs, settings, environment, outputs and outcome.
- **Run_Status**: One of `succeeded`, `failed` or `timed_out`.
- **CODA_Files**: The sample exports written by `samplesCoda`: one index file and one file per chain.
- **Published_Baseline**: The mean, standard deviation and Monte Carlo error values for the Monitored_Nodes, transcribed by eye from the results image in the OpenBUGS 3.2.3 Seeds example page.
- **Tolerance_Rule**: The pass criterion for a node: the absolute difference between the computed mean and the Published_Baseline mean is at most 4 times the Published_Baseline MC_error, and the absolute difference between the computed standard deviation and the Published_Baseline standard deviation is at most 10 percent of the Published_Baseline standard deviation.
- **Comparator**: The ReproLab code that computes means and standard deviations from CODA_Files and applies the Tolerance_Rule.
- **Pre-declared_Comparison**: The comparison made with the settings and Tolerance_Rule fixed before any results were viewed.
- **Post_Hoc_Analysis**: Any comparison or run whose settings (chain selection, burn-in, seed) were chosen after viewing results.
- **Feasibility_Record**: The document `docs/engine-feasibility.md`.
- **Notices_Document**: The document `docs/third-party-notices.md`.
- **Web_Runner**: The later hosted service that runs analyses for users. It is not part of this milestone.
- **Evidence_Directory**: The directory `docs/evidence/` that holds the raw files from each Run.
- **ReproLab_Code**: The adapter, scripts, tests, Dockerfile and documents written for this project.
- **Upstream_Component**: Any part of the Engine_Image or its inputs that ReproLab did not write: the OpenBUGS wrapper and library, the BlackBox and CpcBeautifier parts, TAUCS, the example and documentation files, and the Debian packages.
- **Image_Distribution**: Any step that makes the Engine_Image, its layers or the OpenBUGS files in it available to anyone outside the building machine, including a registry push, a release asset, a download link, an exported or saved file given to someone, and a copy in a hosted image store. A local build and local test Runs are not Image_Distribution.
- **Release_Gate**: The four gates G1 provenance, G2 licence obligations, G3 matching source and G4 recorded decision, as defined in the Release_Decision_Record.
- **Release_Decision_Record**: The document `docs/release-decision.md` with its Decision log.

## Requirements

### Requirement 1: Record engine provenance

**User Story:** As a researcher, I want the origin of the engine recorded exactly, so that I can judge whether the binary I rely on is the one the OpenBUGS project released.

#### Acceptance Criteria

1. THE Feasibility_Record SHALL state the OpenBUGS version, the engine banner text, the source URL, the pinned commit or reference of that URL, and the SHA-256 of the source archive.
2. THE Feasibility_Record SHALL quote the licence statement found in the archive file `COPYING`, naming each licence version and each bundled component it mentions.
3. THE Feasibility_Record SHALL list the exact commands used to configure, build and install the engine.
4. IF the SHA-256 of the source archive could not be compared with a checksum published by the upstream OpenBUGS project, THEN THE Feasibility_Record SHALL state that the comparison was not done and give the reason, namely that SourceForge returns an HTML page for scripted downloads.
5. THE Feasibility_Record SHALL state that the engine library `libOpenBUGS.so` is a prebuilt 32-bit Intel 80386 binary whose source is not in the Linux archive.
6. THE Feasibility_Record SHALL link to the raw archive inspection output stored in the Evidence_Directory.

### Requirement 2: Build a pinned Linux x86-64 environment

**User Story:** As a developer, I want a pinned and verifiable image, so that I can rebuild the same engine environment and detect a tampered download.

#### Acceptance Criteria

1. THE Engine_Image SHALL be built for the linux/amd64 platform from a base image referenced by SHA-256 digest.
2. WHEN the Engine_Image build downloads the OpenBUGS source archive, THE Dockerfile SHALL compare the archive SHA-256 with the recorded value and stop the build on a mismatch.
3. THE Engine_Image SHALL run the engine and the Adapter as a non-root user.
4. WHEN `OpenBUGS --help` is executed in the Engine_Image, THE OpenBUGS binary SHALL exit with status 0 and print its usage text.
5. WHEN a Run starts, THE Adapter SHALL record the engine banner version in the Run_Manifest.
6. THE Feasibility_Record SHALL state the image identifier used for every Run and state whether that identifier is a local image ID or a registry digest, and the identifier SHALL be a local image ID unless a registry digest exists after an approved Image_Distribution.
7. THE Feasibility_Record SHALL state which parts of the build are not pinned, including operating system package versions.
8. THE Feasibility_Record SHALL provide the command sequence that lets another developer rebuild the Engine_Image and repeat a Run.
9. IF any gate of the Release_Gate is unmet, THEN THE Feasibility_Harness SHALL NOT create a registry digest by pushing the Engine_Image.

### Requirement 3: Run the Seeds example with explicit settings

**User Story:** As a researcher, I want the Seeds tutorial run with every setting written down, so that I can see exactly what the engine was asked to do.

#### Acceptance Criteria

1. WHEN a Seeds Run is requested, THE Adapter SHALL generate a Batch_Script that checks the model, loads the data, compiles two chains, loads one initial-value file per chain, applies the burn-in, sets the Monitored_Nodes, performs the sampling updates, writes CODA_Files and quits.
2. THE Seeds_Example SHALL use the data with 21 plates, the model file, the data file, and two separate initial-value files, one for each chain.
3. WHEN a Seeds Run is requested, THE Adapter SHALL monitor `alpha0`, `alpha1`, `alpha2`, `alpha12` and `sigma`.
4. THE Adapter SHALL take the burn-in length, the number of sampling updates, the random-number seed and the timeout as explicit arguments and write them to the Run_Manifest.
5. THE Adapter SHALL start the engine from an argument list without a shell, with the form `OpenBUGS -t <script>`.
6. WHEN a Run ends, THE Adapter SHALL save the engine standard output as the log file and the engine standard error as a separate file.
7. IF a model name, file name, node name or setting contains a character outside the allowed set, THEN THE Adapter SHALL reject the request before writing the Batch_Script and report which value was rejected.
8. WHILE upstream example licensing is unresolved, THE Feasibility_Harness SHALL read the Seeds model, data and initial-value files from the Engine_Image and SHALL NOT commit copies of them to the repository.
9. THE Feasibility_Record SHALL record the SHA-256 of each upstream Seeds input file.

### Requirement 4: Record every Run in a manifest

**User Story:** As a researcher, I want each Run described in one file, so that I can audit or repeat it.

#### Acceptance Criteria

1. WHEN a Run ends, THE Adapter SHALL write a Run_Manifest that contains the generated Batch_Script text, the engine argument list, the engine exit status, the Run_Status, the engine runtime in seconds, the engine banner version and the Engine_Image identifier.
2. THE Run_Manifest SHALL contain the SHA-256 of every input file and the SHA-256 of every output file, including the log, the standard error file and each of the CODA_Files.
3. THE Run_Manifest SHALL contain the burn-in length, sampling updates, seed, timeout and Monitored_Nodes used.
4. THE Run_Manifest SHALL be valid JSON, and FOR ALL Run_Manifest objects, parsing the written file and serializing the result SHALL produce an equivalent object (round-trip property).
5. IF the Run_Manifest cannot be written, THEN THE Adapter SHALL exit with a non-zero status and print the reason.
6. THE Evidence_Directory SHALL contain the Run_Manifest, script, log, standard error file and container state file of each Run named in the Feasibility_Record.

### Requirement 5: Decide the outcome from the log and expected files

**User Story:** As a researcher, I want a Run called successful only when the engine really did the work, so that a silent failure is not reported as a result.

#### Acceptance Criteria

1. THE Adapter SHALL decide the Run_Status from the engine log and from the presence of the expected output files, and SHALL NOT decide it from the engine exit status alone.
2. WHEN the engine log contains the ordered set of success messages for model check, data load, compilation, initialization and sampling, and every expected CODA_File exists and is non-empty, THE Adapter SHALL set the Run_Status to `succeeded`.
3. IF the engine log contains a known error message, THEN THE Adapter SHALL set the Run_Status to `failed` even when the engine exit status is 0.
4. IF an expected output file is missing or empty, THEN THE Adapter SHALL set the Run_Status to `failed` and name the missing file.
5. IF the engine process runs longer than the timeout, THEN THE Adapter SHALL terminate the engine process and set the Run_Status to `timed_out`.
6. THE Feasibility_Record SHALL state that the engine returned exit status 0 for both invalid-model cases that were tested.
7. THE Adapter SHALL classify every Run into exactly one of the Run_Status values `succeeded`, `failed` or `timed_out`.
8. THE Adapter test suite SHALL classify the verbatim log text of the real succeeded Run and of each real failed Run into the correct Run_Status.

### Requirement 6: Compare results to the published baseline with a stated tolerance

**User Story:** As a researcher, I want the comparison rule fixed before I see results, so that a pass cannot be produced by tuning the rule.

#### Acceptance Criteria

1. THE Feasibility_Record SHALL state the Tolerance_Rule in a section written before the results of the first comparison, and SHALL repeat it unchanged with the results.
2. THE Comparator SHALL compute the mean and standard deviation of each Monitored_Node from the CODA_Files, and SHALL NOT use the statistics table printed by the engine.
3. WHEN the Comparator evaluates a node, THE Comparator SHALL report a pass only if both conditions of the Tolerance_Rule hold.
4. WHEN the Comparator evaluates a Run, THE Comparator SHALL exit with status 0 only if all five Monitored_Nodes pass.
5. THE Feasibility_Record SHALL state that the Published_Baseline was transcribed by eye from an image, that transcription errors are possible, and that the source page does not state the number of chains.
6. THE Feasibility_Record SHALL report the Pre-declared_Comparison result for each Monitored_Node, including the computed values and the baseline values.
7. WHEN the Pre-declared_Comparison fails, THE Feasibility_Record SHALL report the failure with the same prominence as any later pass.
8. THE Feasibility_Record SHALL label every Post_Hoc_Analysis as post hoc, including single-chain comparisons and comparisons made with a changed burn-in.
9. IF settings are changed after a failed comparison, THEN THE Feasibility_Record SHALL disclose that the change followed the failure and give the settings before and after.
10. THE Feasibility_Record SHALL state that matching the Published_Baseline does not establish convergence or scientific validity, and SHALL make no convergence claim without a validated diagnostic method.
11. THE Comparator test suite SHALL include a case where a node passes and a case where a node fails each of the two Tolerance_Rule conditions.

### Requirement 7: Reproduce output with a fixed seed

**User Story:** As a researcher, I want the same seed to give the same samples, so that a rerun can be verified byte for byte.

#### Acceptance Criteria

1. THE Adapter SHALL set the engine random-number generator with `modelSetRN` using a seed from 1 to 14 before the initial values are loaded.
2. THE Adapter SHALL reject a seed outside the range 1 to 14 before running the engine.
3. WHEN two Runs use the same inputs, settings, seed and Engine_Image, THE Feasibility_Harness SHALL produce CODA_Files with identical SHA-256 values.
4. WHEN two Runs differ only in seed, THE Feasibility_Harness SHALL produce CODA_Files with different SHA-256 values.
5. THE Feasibility_Record SHALL state that determinism was shown for one image on one machine and was not shown across machines.
6. IF CODA_Files from a rerun on another machine differ from the recorded SHA-256 values, THEN THE Feasibility_Record SHALL direct the developer to record the difference.

### Requirement 8: Preserve real errors and handle timeout and cleanup

**User Story:** As a researcher, I want failures to show the engine's own words, so that I can understand what went wrong without invented explanations.

#### Acceptance Criteria

1. WHEN the Adapter runs a model with a syntax error, THE Feasibility_Harness SHALL preserve the verbatim engine log and set the Run_Status to `failed`.
2. WHEN the Adapter runs a model that refers to an undefined node, THE Feasibility_Harness SHALL preserve the verbatim engine log and set the Run_Status to `failed`.
3. THE Feasibility_Record SHALL quote the first engine error line for each invalid-model case.
4. THE Evidence_Directory SHALL contain the invalid models used for the two failure cases or reference their location in the repository.
5. WHEN a Run exceeds its timeout, THE Adapter SHALL terminate the engine, preserve the partial log and set the Run_Status to `timed_out`.
6. WHEN a Run ends with any Run_Status, THE Feasibility_Harness SHALL remove the temporary container and the temporary volume of that Run after copying the output files out.
7. THE Feasibility_Record SHALL list the failure modes that were not tested, including out-of-memory termination, a full disk and concurrent Runs.

### Requirement 9: Respect Linux and storage constraints

**User Story:** As a developer, I want the engine's Linux limits documented, so that later code does not depend on commands that do not exist.

#### Acceptance Criteria

1. THE Adapter SHALL NOT emit the script commands `modelDisplay` or `modelSaveLog`, which the Linux engine rejects as unknown commands.
2. THE Feasibility_Record SHALL state that on Linux the engine writes its log to standard output.
3. THE Feasibility_Harness SHALL execute each Run on container-local storage and SHALL NOT use a Windows bind mount as the engine working directory, because the engine failed with a file seek error on a Windows bind mount.
4. THE Feasibility_Record SHALL quote the engine error message observed on the Windows bind mount.
5. THE Adapter test suite SHALL verify that a generated Batch_Script contains neither `modelDisplay` nor `modelSaveLog`.

### Requirement 10: Apply an isolation baseline to feasibility Runs

**User Story:** As a project maintainer, I want the feasibility Runs executed with restricted privileges, so that the evidence reflects a safer setup than a default container.

#### Acceptance Criteria

1. WHEN the Feasibility_Harness starts a Run container, THE Feasibility_Harness SHALL disable networking, mount the root filesystem read-only, drop all Linux capabilities and set the no-new-privileges option.
2. WHEN the Feasibility_Harness starts a Run container, THE Feasibility_Harness SHALL set a process-count limit, a memory limit and a CPU limit and SHALL run as a non-root user.
3. THE Feasibility_Record SHALL list the exact container flags and limit values used.
4. THE Feasibility_Record SHALL state that these Runs were made on Docker Desktop on a developer machine and are not a test of the production sandbox.
5. THE Feasibility_Record SHALL state that public custom uploads remain disabled until isolation is tested on the intended worker host.
6. THE Feasibility_Harness SHALL enable no public model upload feature in this milestone.

### Requirement 11: Resolve or record licence and notice questions

**User Story:** As a project maintainer, I want every open licence question written down, so that nothing is redistributed or licensed on an assumption.

#### Acceptance Criteria

1. THE Notices_Document SHALL record that the archive `COPYING` file names GPL version 3 while the SourceForge project page names GPL version 2, that the archive also contains a GPL version 2 text at `doc/Manuals/GNU-Licence.html`, and that upstream revision r1018 ("Clarified licence of libOpenBUGS.so", 2014-07-09) postdates the archive dated 2014-03-06 and is not in the archive `COPYING`.
2. THE Notices_Document SHALL record that `libOpenBUGS.so` is distributed prebuilt without its Component Pascal source in the Linux archive.
3. THE Notices_Document SHALL record the BlackBox Component Builder and CpcBeautifier components named in the archive and the terms the archive states for them, SHALL record the BlackBox Open Source License conditions found in the upstream file `Docu/BB-Open-Source-License.odc`, and SHALL record that the CpcBeautifier licence is unknown and that the TAUCS status is unknown.
4. THE Notices_Document SHALL record the open question of whether the OpenBUGS example files and documentation may be redistributed in this repository.
5. THE Notices_Document SHALL record the open question of which licence the ReproLab_Code will use.
6. WHILE the example redistribution question is open, THE Feasibility_Harness SHALL NOT commit upstream example model, data or initial-value files to the repository.
7. THE repository SHALL NOT contain a root `LICENSE` file for the ReproLab_Code as a result of this milestone, the Feasibility_Record SHALL state that no licence has been chosen for the ReproLab_Code, and the Notices_Document SHALL state that the choice belongs to the next milestone after legal review.
8. THE Notices_Document SHALL NOT claim ownership of OpenBUGS or of its examples.
9. THE Notices_Document SHALL state that the licence chosen for the ReproLab_Code grants no rights over any Upstream_Component, and SHALL record any permission to redistribute an Upstream_Component separately for each Upstream_Component.
10. WHILE any licence question in the Notices_Document is open, THE Notices_Document and THE Feasibility_Record SHALL state that the licence review is incomplete.
11. THE Notices_Document, THE Feasibility_Record and every other document of this milestone SHALL NOT describe the licence review as complete.

### Requirement 12: Record the go/no-go decision

**User Story:** As a project maintainer, I want a written decision with its conditions, so that later work does not proceed on an overstated result.

#### Acceptance Criteria

1. THE Feasibility_Record SHALL contain a decision section that states GO or NO-GO separately for the engine, for Image_Distribution and for the Web_Runner.
2. IF the engine build fails, or no Seeds Run reaches the Run_Status `succeeded`, THEN THE Feasibility_Record SHALL state NO-GO for the engine and SHALL NOT describe the engine as working.
3. WHILE any gate of the Release_Gate is unmet, THE Feasibility_Record SHALL state NO-GO for Image_Distribution and for the Web_Runner.
4. WHILE the isolation baseline has not been tested on the intended worker host, THE Feasibility_Record SHALL state NO-GO for the Web_Runner.
5. THE Feasibility_Record SHALL state which results are available: the engine runs the Seeds_Example; the chain 1 only comparison matched the Published_Baseline in a Post_Hoc_Analysis; the pooled two-chain comparison with 1,000 burn-in updates did not match on any Monitored_Node in the Pre-declared_Comparison; the pooled two-chain comparison with 20,000 burn-in updates matched all five Monitored_Nodes.
6. THE Feasibility_Record SHALL state that the 20,000 burn-in setting was chosen after the 1,000 burn-in comparison failed, and that the pass is therefore a post hoc result and not an independent confirmation.
7. THE Feasibility_Record SHALL list the open uncertainties, including the unverified upstream checksum, the eye-transcribed baseline, unpinned operating system packages, the missing registry digest, the untested production isolation, the unknown build revision of `libOpenBUGS.so`, the GPL version 2 and version 3 conflict, the unknown CpcBeautifier and TAUCS terms, and the unknown rights to the example data.
8. WHERE a later spec depends on a working engine, THE spec SHALL cite the decision section of the Feasibility_Record.
9. IF the Run evidence for the Seeds_Example is missing from the Evidence_Directory, THEN THE Feasibility_Record SHALL NOT mark the corresponding task as complete.

### Requirement 13: Gate Image_Distribution

**User Story:** As a project maintainer, I want publication blocked until the obligations are met, so that nothing is distributed on an assumption.

#### Acceptance Criteria

1. WHILE any gate of the Release_Gate is unmet, THE Feasibility_Harness SHALL NOT perform Image_Distribution, and no script, CI job or document of the repository SHALL contain a step that performs Image_Distribution.
2. THE Release_Decision_Record SHALL define gate G1 as met only when the SHA-256 of the source archive matches a value obtained from SourceForge by browser download or from the OpenBUGS maintainer, and the build revision of the distributed `libOpenBUGS.so` is known.
3. THE Release_Decision_Record SHALL define gate G2 as met only when all of the following hold: the GPL version 2 and version 3 conflict is resolved; the Engine_Image contains the GPL version 3 text, the upstream r1018 `COPYING`, the BlackBox licence text and the component notices; the CpcBeautifier and TAUCS terms are answered; the policy for the Examples, GeoBUGS and Reliability material is implemented by obtaining permission or by excluding that material from the distributed image; the Debian copyright notices are kept; and a legal review is recorded.
4. THE Release_Decision_Record SHALL define gate G3 as met only when a written source pointer or offer for `libOpenBUGS.so` names the SVN revision and the toolchain of the distributed binary, and a Debian source offer or pinned Debian package versions exist.
5. THE Release_Decision_Record SHALL define gate G4 as met only when its Decision log contains an entry that names the date, the decider and the exact image digest, and links the evidence for gates G1, G2 and G3.
6. THE Release_Decision_Record SHALL state NO-GO by default, and a Decision log entry that approves distribution SHALL be added only when gates G1, G2 and G3 are met.
7. THE Feasibility_Harness SHALL cite the Decision log entry of the Release_Decision_Record in every step that performs Image_Distribution.
8. WHEN the Engine_Image is rebuilt after a gate was recorded as met, THE Release_Decision_Record SHALL require the evidence for that gate to be re-verified against the digest of the new image.
9. THE Feasibility_Harness SHALL provide a guard that fails when the Decision log has no approval entry for the digest of the Engine_Image, and the guard SHALL exist before any Image_Distribution step is added. The guard is a requirement for a later task and does not exist in this milestone.
